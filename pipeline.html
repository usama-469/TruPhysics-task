00 The whole loop

Eight stages, once per frame, with no state carried between them

There is no filter, no tracker and no prediction in v1. Every frame is solved from scratch, so every wobble in the map is real measurement noise rather than a smoother’s lag. The only thing that survives across frames is the drawn trail — and that is display, not estimation.

01 Frame source

Three input kinds behind one read()

A webcam index, a video file or stream URL, and a folder of stills all have to work. The recorded-clip path is not a convenience: replaying a file is the only way to get a repeatable number out of a run, and the stills path is what the measurement scripts feed on.

On a live camera, autofocus and auto-exposure are switched off before anything else happens. Autofocus hunting changes the principal distance mid-run, which changes apparent tag size, which changes recovered range and position — it looks exactly like algorithm failure. Every property is written and then read back, because most backends accept the write and ignore it.

frame: ndarray (H, W, 3) uint8 BGR, or None at exhaustion
First-frame guard. If calib.npz carries an image_size, frame 0 is checked against it and the run aborts on a mismatch. A phone’s stills and its video are different aspect ratios and different sensor crops, so a stills calibration on a video stream produces a confident, wrong position with no visible symptom.

02–03 Detection

Greyscale in, corners and IDs out

Detection runs on a single channel; the colour frame is kept only so the overlay can be drawn on it. DICT_4X4_50 is the smallest dictionary that covers nine tags, and small matters: fewer bits per tag means physically larger, more robust bit cells at a given printed size, which is what decides whether a tag at range resolves at all.

Sub-pixel corner refinement is on and it is not cosmetic. Corner localisation error propagates roughly linearly into recovered position. At the real 12 m ceiling one pixel is about 3 mm on the marker plane, so whole-pixel versus 0.1 px corners is the difference between a millimetre-level and a sub-millimetre line in the error budget.

in
gray: (H, W) uint8
out
corners: list of (1, 4, 2) float32 · ids: (N, 1) int32 · rejected

04 Known / unknown split

A tag with no surveyed position cannot contribute a correspondence

Detected IDs are partitioned against the keys of markers.json. Unmapped tags are kept in their own bucket rather than dropped, and drawn in red on the camera window, because a tag that is physically on the ceiling but missing from the map is the single most common surveying mistake — and silently discarding it would hide it.

known
[(id, corners), ...] — feeds the solve
unknown
[(id, corners), ...] — overlay only, red

05 Correspondence build

The handedness trap, and where it is resolved

Each detected marker contributes four 3D–2D pairs. The 3D side comes from the marker’s surveyed centre plus a corner offset; the 2D side is the refined image corner. The only question is which offset pairs with which image corner — and that mapping is fixed by geometry, not by taste.

ArUco returns corners clockwise as printed on the tag, so index 0 is a fixed physical corner regardless of camera rotation. What is not fixed is which side of the marker plane the camera sits on: viewed from below, the winding that appears clockwise in the image traverses the world square the other way round. Get it wrong and X or Y comes out mirrored.

A refined map (from tools/refine_map.py) may give a tag its own solved height and in-plane yaw, since printed sheets taped up by hand are neither exactly coplanar nor exactly square. Both are applied here rather than assumed away.

out
objectPoints: (4N, 3) float64 · imagePoints: (4N, 2) float64 · used_ids

06 Inside solvePnP

One fused solve, chosen from three branches

All visible markers’ corners go into a single solvePnP call. Solving each marker separately and averaging would throw away exactly what makes the multi-marker case well conditioned: the markers’ positions relative to each other are known, so their combined outline constrains camera orientation far more tightly than any one tag’s four corners can.

Why ITERATIVE and not a planar-specific flag. For a coplanar point set OpenCV initialises ITERATIVE from a homography — the closed-form planar solution — then refines by Levenberg–Marquardt. It is already a planar solver in one call, so the known common plane is exploited rather than merely tolerated.

07 Inversion and heading

solvePnP tells you where the world is. You want where the camera is.

rvec and tvec map world into the camera frame. The camera’s own position is the origin of the camera frame expressed in world coordinates, which is the inverse transform applied to zero: C = −Rᵀ t. C[0] and C[1] are the reported X and Y; C[2] is logged too, because the marker map pins the plane at a known Z, so solved camera Z is a free readout of range error — and a range off by a fixed fraction means the focal length is off by that same fraction, which scales X and Y with it.

08 Quality

An accuracy number derived, not asserted

Ground sampling distance is how many metres on the marker plane one pixel covers: range / focal_px. Multiplying by the mean reprojection error converts the residual the solver actually saw into a distance. Dividing by √n reflects that independent corner noise averages down across markers.

acc_est_m = (range_m / focal_px) × reproj_px / √n_markers
            ⌙              ⌙            ⌙
       metres per pixel   what the solver   independent
       at solved range    could not fit     corner noise

The range used is the solved camera-to-plane distance rather than the nominal ceiling height, because that is the distance the pixels were actually projected over.

What this number deliberately excludes. Marker placement survey error (±8 mm here) and camera tilt. Both belong in the report’s error budget as their own rows. Survey error is a property of how the tags were measured, never of the algorithm; folding it in would make a badly surveyed rig look like a badly performing solver.

Visualization

How the 2D hall map is built, and what feeds every mark on it

The map is a second named OpenCV window drawn with primitives — no matplotlib, no render thread. It earns its place because it makes a wrong pose obvious at a glance: a mirrored X, a tag mapped to the wrong grid cell, a jump the instant a marker leaves view. None of those are visible in a scrolling column of numbers.

The extent is derived, never configured

Bounds come from the min and max of the marker positions themselves. A hand-entered hall rectangle would be a second copy of the same fact, free to drift out of agreement with the first. The view is then widened by the current trail, not by every pose ever seen — so a single ill-conditioned single-marker frame that lands metres away zooms the map out only until it ages past the trail length, then the scale recovers on its own.

reproj_px is on the map’s absent list on purpose. It is a fit statistic, not an accuracy — on this rig it mostly reports how well the marker survey is known. It stays in logs/track.csv, where the report needs it, and off the display, where it invites being read as a position error.

Outputs

One CSV row per frame, one datagram per fix

The CSV logs frames with no pose as blank rows rather than skipping them: the fraction of frames that yielded a fix is itself a result, and it cannot be recovered from a file that only kept the successes. It is opened for append, because overwriting would silently destroy the run the report is being written from.

t, frame, x_m, y_m, z_m, yaw_deg, tilt_deg, n_markers,
ids, reproj_px, acc_est_m, single_marker, level_assumed

z_m is logged alongside X and Y as the free scale check: the map pins the plane at a known Z, so solved camera Z reads out range error directly.

UDP, one datagram per fix

Fire-and-forget to 127.0.0.1:5005. A consumer that stalls or dies must not slow the capture loop or block a frame; a dropped datagram costs one pose and the next is along in ~30 ms. The payload stays flat so a ROS 2 bridge node is a field-by-field copy.

{"t": 1723459200.12, "x": 0.912, "y": 0.744, "yaw_deg": 91.3,
 "markers": [4, 5, 7, 8], "reproj_px": 0.38, "acc_est_m": 0.0038}

The log is written before the send, so a publish that raises never costs the row.

Scaled demonstrator. The rig is a 2.400 m ceiling with 0.1435 m tags, chosen to hold angular size roughly constant against the real case — a 15 cm tag at 2.5 m subtends about the same angle as a 72 cm tag at 12 m. Moving to the hall changes those two config numbers. No code path differs.
